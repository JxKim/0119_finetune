# 大模型推理和评估概念小测

## 大模型推理框架的原理

1. 简要介绍一下pagedAttention

<details>
<summary>参考答案</summary>

PagedAttention 是 vLLM 中用来管理 KV Cache 的核心机制。

大模型自回归生成时，每生成一个 token，都需要保存前面 token 的 Key / Value，这部分缓存叫 KV Cache。随着 batch 变大、上下文变长，KV Cache 会占用大量显存，而且不同请求的长度不一样，容易造成显存碎片和浪费。

PagedAttention 的思路类似操作系统里的分页内存管理：

- 把 KV Cache 切成固定大小的 block。
- 每个请求不需要一开始就申请一整块连续显存。
- 请求生成到哪里，就按需分配对应的 KV Cache block。
- 不同请求的 KV Cache 可以以非连续的方式存放，再通过映射关系组织起来。

这样可以显著提升显存利用率，减少显存碎片，让推理服务能够同时处理更多请求。

</details>

2. 简要介绍一下连续批处理

<details>
<summary>参考答案</summary>

连续批处理一般指 continuous batching，是大模型推理服务中提高吞吐量的重要机制。

传统 batch 推理通常要等同一个 batch 里的所有请求都生成完成后，才能处理下一批请求。但大模型生成任务中，不同请求的输入长度、输出长度差异很大，如果某些请求很快结束，GPU 资源就会被浪费。

连续批处理的核心思想是：

- 服务端持续接收新请求。
- 每一步生成时，把当前还没完成的请求组成一个动态 batch。
- 某些请求生成结束后，立刻把新请求补进来。
- 不需要等待整个 batch 全部完成。

它的好处是可以提高 GPU 利用率和整体吞吐量，尤其适合在线推理服务中请求不断到来的场景。

需要注意的是，连续批处理主要提升吞吐量，但如果排队请求太多，也可能增加部分请求的等待时间。

</details>

3. 单机多卡，一般通过什么方式去部署模型？

<details>
<summary>参考答案</summary>

单机多卡部署大模型时，常见方式是使用张量并行，也就是 tensor parallel。

原因是大模型参数量很大，单张 GPU 可能放不下完整模型，或者虽然能放下但显存压力很大。张量并行会把模型中的大矩阵计算拆分到多张 GPU 上，每张卡保存和计算其中一部分参数。

在 vLLM 中，常见参数是：

```bash
--tensor-parallel-size 2
```

或者：

```bash
--tensor-parallel-size 4
```

表示把模型切到 2 张或 4 张 GPU 上部署。

实际选择时通常看几个因素：

- 模型大小：模型越大，越可能需要更多 GPU。
- 单卡显存：显存不够时需要增加 tensor parallel size。
- 推理吞吐：多卡可以提升计算能力，但也会引入卡间通信开销。
- GPU 数量：`tensor-parallel-size` 一般要和可用 GPU 数量匹配。

如果是单机部署一个大模型服务，最常见的就是 vLLM + tensor parallel。

</details>

## 大模型部署压测

1. 评估大模型推理性能的指标有哪些，可以分为哪两个方面

<details>
<summary>参考答案</summary>

评估大模型推理性能的指标，通常可以分为两个方面：吞吐量和延迟。

吞吐量相关指标主要看服务整体处理能力：

- QPS：每秒能处理多少个请求。
- Tokens/s：每秒生成多少 token。
- 总吞吐量：在一定并发下，系统整体输出能力。
- 并发能力：同时处理多少请求时服务仍然稳定。

延迟相关指标主要看单个请求的体验：

- TTFT：Time To First Token，首 token 延迟，即用户多久能看到第一个输出。
- TPOT：Time Per Output Token，平均每个输出 token 的生成耗时。
- 总响应时间：一个请求从发出到完整生成结束的耗时。
- P50 / P90 / P99 延迟：不同分位数下的延迟表现，尤其 P99 能反映长尾问题。

简单来说：

- 吞吐量关注“系统每秒能服务多少请求 / 生成多少 token”。
- 延迟关注“单个用户等多久能得到响应”。

实际压测时不能只看一个指标。比如只追求高吞吐，可能会让首 token 延迟变高；只追求低延迟，也可能导致 GPU 利用率不足。

</details>


2. 如何通过修改vLLM的部署参数，来优化大模型的推理性能？

<details>
<summary>参考答案</summary>

vLLM 的推理性能可以从显存利用、并发数量、上下文长度、并行方式和生成配置几个方向优化。

常见参数和思路如下：

1. 调整 `--gpu-memory-utilization`

这个参数控制 vLLM 可以使用多少比例的 GPU 显存。

适当调高可以给 KV Cache 留出更多空间，从而支持更高并发或更长上下文。例如从 `0.8` 调到 `0.9`。

但不能无限调高，否则容易因为系统开销、显存碎片或其他进程占用导致 OOM。

2. 调整 `--max-model-len`

这个参数控制模型服务允许的最大上下文长度。

如果业务实际不需要特别长的上下文，可以适当降低 `max-model-len`，减少 KV Cache 预留压力，提高可承载并发。

3. 调整 `--max-num-seqs`

这个参数控制一次调度中最多处理多少个序列。

调大可以提高并发能力和吞吐量，但也会增加显存压力，并可能让单个请求的延迟变高。

4. 调整 `--max-num-batched-tokens`

这个参数控制一个 batch 中最多处理多少 token。

调大通常有利于提高 GPU 利用率和吞吐量，但可能增加调度等待和显存占用。调小则可能降低延迟，但吞吐量也会下降。

5. 调整 `--tensor-parallel-size`

如果单卡显存不够，或者模型较大，可以使用张量并行把模型拆到多张 GPU 上。

多卡部署可以解决显存不足问题，也可能提升吞吐，但会引入卡间通信开销，所以不是越大越好。

6. 使用合适的量化方式

如果模型支持量化，可以使用 FP8、AWQ、GPTQ 等方式降低权重显存占用，提高可部署模型规模或并发能力。

但量化可能带来精度损失，需要结合评估结果确认效果是否可接受。

7. 控制生成参数

业务侧的 `max_tokens`、输入长度、输出长度也会直接影响性能。

输出 token 越多，请求占用 GPU 的时间越长；上下文越长，prefill 阶段越慢，KV Cache 占用也越大。

所以优化时一般不是只改一个参数，而是结合压测结果观察：

- 如果显存快满、并发上不去，优先看 `gpu-memory-utilization`、`max-model-len`、量化和 tensor parallel。
- 如果吞吐低，优先看 `max-num-seqs`、`max-num-batched-tokens` 和 batch 调度。
- 如果首 token 延迟高，重点看输入长度、并发压力、batch token 限制和排队情况。
- 如果长尾延迟明显，重点看并发是否过高、请求长度是否差异太大。

</details>

## 大模型评估

1. 为什么大模型评估时不能只看训练 loss？

<details>
<summary>参考答案</summary>

训练 loss 只能说明模型在训练数据上预测下一个 token 的平均误差变小了，但它不能完整代表模型在真实任务中的表现。

不能只看 loss 的原因：

- 训练 loss 下降，不一定说明模型在新数据上泛化更好，可能只是记住了训练数据。
- 对生成任务来说，loss 低不一定等于输出格式正确、内容可用、符合业务要求。
- 微调任务通常更关心最终生成结果，比如关键词是否抽对、回答是否准确、格式是否稳定。
- 如果没有独立验证集或测试集，就很难判断模型是能力提升还是过拟合。

所以评估大模型时，通常需要准备独立的验证集 / 测试集，并结合自动指标、人工评估或 LLM-as-a-judge 来看实际生成效果。

</details>

2. 什么是 LLM-as-a-judge？它适合评估哪些传统指标不好衡量的任务？

<details>
<summary>参考答案</summary>

LLM-as-a-judge 是指使用一个更强或更稳定的大模型作为裁判模型，对被评估模型的输出进行打分或判断。

它的基本流程是：

1. 给被评估模型输入题目，得到模型输出。
2. 把题目、参考答案、模型输出一起交给裁判模型。
3. 让裁判模型按照预先写好的评分规则，输出分数、等级或合格 / 不合格判断。

它适合评估传统自动指标不好衡量的生成任务，比如：

- 问答质量评估。
- 摘要质量评估。
- 指令遵循能力评估。
- 关键词抽取、信息抽取等存在同义表达和顺序变化的任务。
- 开放式回答的相关性、完整性、格式合规性评估。

优点是比较灵活，能处理语义相近但字面不完全一致的答案。缺点是裁判模型本身也可能不稳定、有偏差，所以需要明确评分规则，通常还会把 `temperature` 设置为 `0.0`，让评估结果更稳定。

</details>
